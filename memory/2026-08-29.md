# 2026-08-29 — One colour per tag (first per-topic colour in the design)

## Request
> all distinct tags should have unique color.

## What changed

`assets/app.js` and `assets/style.css` — the first change to the site's visual
system since it was built. No data, no markup.

### The approach, and why not a colour table

The obvious implementation is a `{tag: colour}` map. It was rejected: the whole
point of this repo is that `data/sites.json` is the only file you edit, and a
hard-coded table means every new tag needs a matching CSS edit or it renders
colourless. A name-hash → hue is the other obvious option, and it is worse
still — hashing *cannot guarantee uniqueness*, which is precisely what was
asked for.

So the hues are **derived from the vocabulary**, in `buildTagHues()`:

```js
const step = 360 / vocabulary.length;   // vocabulary = sorted distinct tags
hues.set(tag, (HUE_OFFSET + i * step) % 360);
```

- **Uniqueness is structural**: n tags, n evenly spaced slots. Two tags cannot
  collide, no matter how the data grows.
- **Separation is maximal**: even spacing is the placement that maximises the
  smallest gap. 13 tags today sit 27.7° apart.
- **No code edit to add a tag** — the wheel re-spaces itself.
- **Deterministic**: the vocabulary is sorted, so a given tag set always
  produces the same colours.
- **The trade, worth knowing:** a *new* tag re-spaces everything, so existing
  tags shift hue. The vocabulary fixes the colours, not the individual tag.
  Accepted — a stable-per-name scheme means hashing, and hashing means
  collisions.

`HUE_OFFSET = 15` rotates the first tag off pure red so a chip is never
mistaken for the editorial `--accent` red used by links.

### OKLCH is what makes the split work

`app.js` writes **only** `--tag-hue` on a chip. Lightness and chroma are theme
tokens (`--tag-l`, `--tag-c`), so:

| token     | light | dark |
| --------- | ----- | ---- |
| `--tag-l` | 0.50  | 0.76 |
| `--tag-c` | 0.14  | 0.14 |

Authoring in OKLCH (not HSL) is the reason one pair of values can serve all 13
hues: OKLCH lightness is perceptual, so a chip at hue 15 and one at hue 208 read
at the same weight, and **one contrast check covers the whole palette**. In HSL
the same lightness value produces a blinding yellow and a near-black blue.

`--tag-lch: var(--tag-l) var(--tag-c) var(--tag-hue)` bundles the three, so the
ink `oklch(var(--tag-lch))`, the border `/ 0.45` and the background wash
`/ 0.07` are guaranteed to be the same colour at different strengths. Hover
firms the same hue rather than introducing a second one. The active-filter
banner chip is painted with the clicked tag's hue too, so the banner matches
the chip.

## Verified

Browser-tested with Playwright (Chromium) against `python3 -m http.server` —
**97 assertions, all passing**:

- 13 distinct tags → **13 distinct painted colours**; every chip of the same tag
  identical; no chip left on the old flat ink colour.
- Contrast measured against the real page background: **worst 5.21:1 (`#learning`)
  in light, 8.47:1 (`#tutorial`) in dark** — both past WCAG AA 4.5:1. Every one
  of the 26 chip/theme combinations checked individually.
- Perceptual separation in Oklab: closest pair `c++`/`art` at ΔE 0.0451 light,
  `reference`/`reading` at 0.0606 dark (~2× a just-noticeable difference).
- Chip treatment: faint wash (α 0.07) and softened border (α 0.45) at rest,
  solid border and deeper wash on hover.
- Banner echoes the clicked chip's exact colour for `learning` / `c++` / `art`,
  and filter counts still derive from the data.
- Nothing regressed: 19 entries, `01…19` numbering, `/ 19` index count, titles
  match the data in order, search (`atlas` → 1, `zzzz` → 0 + empty state),
  search AND tag combined, theme toggles both ways, zero horizontal overflow at
  390px.
- Only console error remains the masthead avatar (blocked in this sandbox).
  Pre-existing. No screenshots left behind.

## Notes / learnings

- **Testing gotcha, cost one run:** Chromium keeps a computed `oklch()` /
  `oklab()` colour **in that space** — `getComputedStyle(el).color` returns
  `"oklch(0.5 0.14 15)"`, not `rgb(...)`. Parsing it with an rgb regex silently
  reads `0.5, 0.14, 15` as an RGB triple and produces confident nonsense
  (my first run "measured" contrast on those numbers). Resolve colours by
  painting them into a 1×1 canvas and reading `getImageData` — that also
  applies the browser's real gamut mapping, which matters here because sRGB
  can't hold `C=0.14` in the yellow-green band and Chromium reduces chroma.
- **Second gotcha:** `body` has `transition: background 0.3s`, so sampling the
  page background straight after clicking the theme toggle returns a
  mid-transition colour and every dark-theme contrast check fails bogusly.
  Wait ~500ms after the toggle.
- Design ceiling worth knowing before adding tags: 13 evenly spaced hues is
  already past the ~8–10 that categorical palettes comfortably distinguish.
  The chips carry their text label, so colour is redundant coding rather than
  the only signal — but **prefer reusing an existing tag to inventing one**,
  the same rule the data already follows for other reasons.
- Carried forward and still true: `curl` to `127.0.0.1` needs `--noproxy '*'`;
  Playwright is global, so `import pw from '/opt/node22/lib/node_modules/playwright/index.js'`
  then destructure; scope tag clicks to `#grid .tag[data-tag="…"]` because
  `#active-filter-tag` also carries `class="tag"`; count cards as
  `#grid .entry:not([hidden])`.
- `ARCHITECTURE.md`'s "One accent, not per-topic color" convention was the
  thing this change overturns, so it was rewritten rather than appended to;
  `README.md` gained the automatic-colour note. `PROMPT.md` got the prompt.
