# 2026-08-31 — Topic filter row + a measurably more distinct tag palette

## Request
> * have a row of the tags before the list so that they can be clicked on and filtered
> * the tag colors are too similar, make them a bit distinct

Two changes, both touching the tag system built on 2026-08-29. No data change —
`sites.json` is untouched and still 19 entries / 13 tags.

## 1. Topic filter row (`index.html`, `app.js`, `style.css`)

A `<nav class="tagbar">` between the masthead and the grid, filled by
`renderTagbar()` from the same sorted vocabulary the colours are derived from —
so it needs no maintenance when `sites.json` grows, and it doubles as a legend
for the palette.

- **All + every topic, once**, alphabetical (the order the hues are assigned
  in). Clicking filters, clicking again clears, **All** resets.
- **Counts follow the search box**, not the catalog total, so the row answers
  "what would this filter actually give me right now". They are computed in
  `applyFilters()` from the text query *only* — deliberately ignoring the
  active tag, because a row that counted its own selection would zero out every
  other topic the moment you picked one.
- **Unreachable topics are disabled, not hidden**, so the row never reflows
  under the cursor. The active chip is never disabled, or the filter would
  become impossible to switch off from the row.
- **Selected chip inverts** — the hue becomes the fill, the page background
  becomes the ink (6.0:1 light / 5.9:1 dark, so the inversion is safe for every
  hue). `aria-pressed` carries the state for screen readers and drives the CSS.

The existing "Filtering by #tag [clear ✕]" banner was left exactly as it was.
It is now somewhat redundant with the row — worth asking before removing it.

## 2. Palette: two dimensions instead of one

The 2026-08-29 scheme was hue-only, and the *reason* the colours read as
similar turned out to be a hard sRGB limit, not a spacing choice: there is no
room for a saturated yellow, green or teal at a lightness dark enough to read
on white, so a third of the wheel is squeezed toward grey no matter how the
hues are spaced. Measured worst pair: **0.043 in Oklab** (`learning`/`math`),
under two JNDs.

Three changes, in order of how much they mattered:

1. **An alternating lightness band.** Even indices render at `--tag-l`, odd at
   `--tag-l-alt` (`app.js` adds `.tag--alt`). This separates neighbours in a
   dimension the gamut cannot squeeze, and is free in contrast terms because
   the alternate band moves *away* from the page background.
2. **An even number of hue slots.** `buildTagColors()` divides 360° by the
   vocabulary size **rounded up to even**, leaving the spare slot empty. Without
   this the alternation cannot close — with 13 tags in 13 slots the first and
   last tag are hue-neighbours in the *same* band, and that pair capped every
   other improvement at 0.041.
3. **Chroma pulled back inside sRGB** (0.19 → 0.11 light, 0.13 dark). See the
   gotcha below; this made the palette *more* separated, not less.

| | light | dark |
| --- | --- | --- |
| `--tag-l` / `--tag-l-alt` | 0.48 / 0.40 | 0.76 / 0.66 |
| `--tag-c` | 0.11 | 0.13 |
| closest pair (Oklab) | 0.043 → **0.077** | 0.063 → **0.107** |
| worst chip contrast | **5.04:1** | **5.22:1** |

Chip wash also went 0.07 → 0.12 so the hue reads as an area rather than eight
pixels of text; hover stops at 0.14, past which the ink loses its AA margin.

## The gotcha that cost two design iterations

**Chromium clips out-of-gamut OKLCH per channel; it does not gamut-map it.**
`oklch(0.42 0.19 42.7)` should become `#822f00` under CSS Color 4 (reduce
chroma, hold L and h) and does in spec-following engines; Chromium paints
`#980000` — different hue, different lightness. My first palette was optimised
against a correct-by-spec model, measured beautifully on paper, and came back
*worse than the original* in the browser. Everything after that was measured by
painting into a canvas and reading pixels back.

The practical rule, now in `LEARNINGS.md`: keep `--tag-c` at or under what sRGB
holds for the tightest hue, because an over-ambitious chroma is not one palette
rendered slightly differently — it is a different palette per browser.

## Verified

Browser-tested with Playwright (Chromium) against `python3 -m http.server` —
**69 assertions, all passing**:

- Nothing regressed: 19 entries, `01…19` numbering, `/ 19` index count, titles
  match the data in order.
- Row lists All + all 13 tags in sorted order, counts match the data, chips are
  real `<button type=button>`, and the row renders above the grid.
- Filtering from the row for `learning` / `c++` / `art`: right cards, chip
  pressed, All released, banner echoes the tag, pressed-chip contrast ≥ 4.5:1,
  and a second click toggles it back off. Card chips and the row stay in sync;
  All and the banner's clear button both reset.
- Searching `"course"` recomputes every count, disables exactly the unreachable
  topics, never drops a chip, combines with a tag filter, and keeps the active
  topic enabled even at zero matches.
- Palette: 13 distinct painted colours per theme, alternation applied to
  exactly the odd indices, closest pair 0.0768 light / 0.1071 dark, worst chip
  contrast 5.04:1 / 5.22:1 measured against each chip's own washed background.
- Same tag renders identically on cards and in the row; theme toggles both
  ways; zero horizontal overflow at 1280 / 900 / 600 / 390px.
- Only console error remains the masthead avatar (blocked in this sandbox).
  Pre-existing. No screenshots left behind.

## Notes

- New file: `LEARNINGS.md` — the OKLCH/Chromium gotcha, the "never parse a
  computed colour as a string" rule from 2026-08-29, the transition-timing trap
  (chip colours transition over 0.15s, so a reading taken right after a click
  is a mid-animation `oklab(...)` interpolation), and the sandbox notes that
  every session so far has re-derived.
- CSS gotcha found and fixed: `.tag:hover` out-specified
  `.tag[aria-pressed="true"]`, so hovering the chip you just selected washed
  its fill back out. The hover rule now excludes pressed chips.
- `README.md` and `ARCHITECTURE.md` both updated — the tag-colour convention
  was rewritten again (it now covers the two dimensions, the even-slot rule and
  the chroma/portability constraint), and the topic row is documented as a view
  of the vocabulary rather than a second source of it.
